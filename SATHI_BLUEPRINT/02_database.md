# 02_database.md — SATHI Database Schema & Architecture

## Overview of Database Tables

The application uses **Supabase PostgreSQL** (Free 500MB tier with Supavisor connection pooling) configured via **Drizzle ORM**. Below is the complete catalog of all 18 database tables, enums, columns, types, constraints, and indexes.

### Enums Defined in PostgreSQL
- `user_role`: `'patient'`, `'caregiver'`, `'family'`, `'doctor'`
- `risk_level`: `'low'`, `'medium'`, `'high'`, `'critical'`
- `dose_status`: `'taken'`, `'missed'`, `'pending'`, `'snoozed'`
- `link_relationship`: `'family'`, `'caregiver'`
- `link_status`: `'active'`, `'revoked'`, `'pending'`, `'rejected'`
- `blood_type`: `'A+'`, `'A-'`, `'B+'`, `'B-'`, `'AB+'`, `'AB-'`, `'O+'`, `'O-'`
- `blood_urgency`: `'low'`, `'normal'`, `'critical'`
- `blood_request_status`: `'open'`, `'fulfilled'`, `'cancelled'`
- `schedule_type`: `'ONCE'`, `'RECURRING'`, `'MEDICATION_LINKED'`
- `reminder_status`: `'pending'`, `'delivered'`, `'failed'`, `'cancelled'`

## Detailed Table Specification & Constraints

### 1. `users`
Accounts for patients, caregivers, family members, and doctors.
- `id`: UUID (Primary Key, Random Default)
- `name`: TEXT (Not Null)
- `email`: TEXT (Not Null, Unique)
- `role`: user_role (Enum)
- `linked_patient_id`: UUID (Foreign Key -> patients.id, Nullable)
- `blood_type`: TEXT
- `allergies`: TEXT
- `emergency_contact_name`: TEXT
- `emergency_contact_phone`: TEXT
- `phone`: TEXT
- `avatar`: TEXT
- `password`: TEXT (Bcrypt hashed)
- `push_token`: TEXT (Firebase / Expo notification token)
- `hospital`: TEXT
- `designation`: TEXT
- `department`: TEXT
- `registration_number`: TEXT
- `specialization`: TEXT
- `relationship_preference`: TEXT
- `anchor_times`: JSONB (Default: `{"morning": "08:00", "afternoon": "14:00", "evening": "20:00", "night": "22:00"}`)
- `is_email_verified`: BOOLEAN (Not Null, Default: false)
- `email_verification_code`: TEXT
- `email_verification_expires`: TIMESTAMP
- `created_at`: TIMESTAMP (Default: now())

### 2. `patients`
Medical profile entities representing individuals undergoing post-discharge recovery.
- `id`: UUID (Primary Key, Random Default)
- `caregiver_id`: UUID (Foreign Key -> users.id, Legacy single-manager link)
- `name`: TEXT (Not Null)
- `age`: INTEGER (Not Null)
- `condition`: TEXT (Not Null)
- `discharge_date`: TIMESTAMP (Not Null)
- `emergency_contact`: TEXT (Not Null)
- `blood_type`: TEXT
- `allergies`: TEXT
- `emergency_contact_name`: TEXT
- `emergency_contact_phone`: TEXT
- `link_code`: VARCHAR(12) (Unique shareable code, e.g. `DB-7G4K2P`)
- `link_code_issued_at`: TIMESTAMP
- `created_at`: TIMESTAMP (Default: now())

### 3. `care_links`
Many-to-many relationship linking patients to multiple managers (caregivers/family).
- `id`: UUID (Primary Key, Random Default)
- `patient_id`: UUID (Foreign Key -> patients.id, Not Null)
- `manager_id`: UUID (Foreign Key -> users.id, Not Null)
- `relationship`: link_relationship (Enum, Not Null)
- `status`: link_status (Enum, Not Null, Default: 'active')
- `created_at`: TIMESTAMP (Default: now())
- **Constraints**: Unique constraint on `(patient_id, manager_id)` (`care_links_patient_manager_unique`).

### 4. `messages`
Real-time 1:1 chat between a patient and a linked manager.
- `id`: UUID (Primary Key, Random Default)
- `sender_id`: UUID (Foreign Key -> users.id, Not Null)
- `receiver_id`: UUID (Foreign Key -> users.id, Not Null)
- `patient_context_id`: UUID (Foreign Key -> patients.id, Not Null)
- `text`: TEXT (Not Null)
- `audio_base64`: TEXT (Nullable voice note recording)
- `created_at`: TIMESTAMP (Default: now())
- **Indexes**:
  - `messages_pair_idx` ON `(patient_context_id, created_at)`
  - `messages_participants_idx` ON `(sender_id, receiver_id)`

### 5. `medicines`
Prescribed medication schedules and dosing instructions.
- `id`: UUID (Primary Key, Random Default)
- `patient_id`: UUID (Foreign Key -> patients.id, Not Null)
- `name`: TEXT (Not Null)
- `dosage`: TEXT (Not Null)
- `frequency`: TEXT (Not Null)
- `times`: TEXT[] (Array of strings like `["08:00", "20:00"]`, Not Null)
- `schedule_time`: TEXT (Not Null, Default: '08:00')
- `is_default_time`: BOOLEAN (Not Null, Default: false)
- `instructions`: TEXT
- `simplified_instructions`: TEXT (Jargon-free version generated by AI)
- `start_date`: TIMESTAMP (Not Null)
- `end_date`: TIMESTAMP
- `color`: TEXT (Default: '#0891b2')
- `total_pills`: INTEGER
- `status`: TEXT (Enum: `'active'`, `'archived'`, Not Null, Default: 'active')
- `plan_id`: UUID (Optional link -> discharge_plans.id)

## Care Links Relationship Model Explained
In SATHI, multiple users (Caregivers, Family Members, Doctors) can monitor and manage a single patient without sharing login credentials. This is powered by the `care_links` table and unique shareable link codes (`link_code`).
1. **Shareable Code Generation**: When a patient account is created or requests a code, a 12-character uppercase alphanumeric string prefixed with `DB-` is generated (e.g., `DB-7G4K2P`). This code expires after 7 days.
2. **Link Creation**: When a caregiver or family member inputs this code via `/api/links/connect`, the server checks `patients.link_code`, verifies expiration, and inserts a record into `care_links` associating `patient_id` and `manager_id` (`users.id`).
3. **Multi-Manager Support**: The table has a composite unique constraint on `(patient_id, manager_id)` to prevent duplicate links. The `relationship` enum (`'family'`, `'caregiver'`) determines UI permissions (e.g., caregivers can add medications and create discharge plans; family members get read-only status and check-in capabilities).
4. **Context Scoping**: In real-time chat, the `messages` table includes `patient_context_id`. Even if Caregiver A manages both Patient X and Patient Y, messages sent to family members regarding Patient X remain strictly partitioned by `patient_context_id`.

## Startup Schema Guard Logic (`ensureSchema.ts`)
To ensure zero-downtime deployments on serverless container platforms (Cloud Run / Render) where running schema migration scripts prior to boot might be skipped or fail, SATHI includes an additive runtime schema guard executed automatically when `index.ts` boots.

```typescript
import { pool } from "@workspace/db";
import { logger } from "./lib/logger";

const STATEMENTS = [
  `CREATE TABLE IF NOT EXISTS messages (
     id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
     sender_id uuid NOT NULL REFERENCES users(id),
     receiver_id uuid NOT NULL REFERENCES users(id),
     patient_context_id uuid NOT NULL REFERENCES patients(id),
     text text NOT NULL,
     audio_base64 text,
     created_at timestamp DEFAULT now()
   );`,
  `ALTER TABLE messages ADD COLUMN IF NOT EXISTS audio_base64 text;`,
  `CREATE INDEX IF NOT EXISTS messages_pair_idx ON messages (patient_context_id, created_at);`,
  `CREATE INDEX IF NOT EXISTS messages_participants_idx ON messages (sender_id, receiver_id);`,
];

export async function ensureSchema(): Promise<void> {
  try {
    for (const sql of STATEMENTS) {
      await pool.query(sql);
    }
    logger.info("Schema guard: chat 'messages' table ensured");
  } catch (err) {
    logger.error({ err }, "Schema guard failed");
  }
}
```

## Migration Approach
1. **Development Migrations**: Run `pnpm --filter @workspace/db run push` (`drizzle-kit push --config ./drizzle.config.ts`). Drizzle introspects the live database, calculates diffs against `./src/schema/index.ts`, and applies DDL directly without generating static SQL migration files.
2. **Production Backfills & Repair**: In CI/CD or production environments, standalone Node scripts in `artifacts/api-server/` (`run_migration.mjs`, `apply-link-schema.mjs`, `apply-messages-schema.mjs`, `backfill-doses.ts`, `backfill-links.mjs`) are executed to guarantee column additions and seed relationships idempotently before traffic routing.
